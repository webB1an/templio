# Templio · 思路可行性与流程拷打

> 版本：v0（讨论稿） · 日期：2026-11-01 · 状态：**未开始开发**
>
> 项目：模板库小程序（用户端）+ 管理端 + 服务端 + 桌面端
> 小程序 UI：Apple 液态玻璃（Liquid Glass）风格
>
> 本文回答三件事：① 你的思路可不可行；② 哪里要优化；③ 哪些地方必须由你拍板。
> 你确认后我出 v1《流程确认稿》，再等你说"开始开发"。

---

## 0. 结论先行

**可行，但不能按你现在的顺序做。**

| 维度 | 判断 | 说明 |
| --- | --- | --- |
| 技术可行性 | 可行 | 无硬阻塞。DeepSeek 已支持图片输入（`deepseek-flash`），"看图识别类型 + 生成标题"成立；批量渲染、小程序展示都是常规工程。 |
| 产品可行性 | 有缺口 | 你描述的是**供给流水线**，缺"用户拿到模板"的最后一公里。用户在小程序里点完模板之后发生什么，决定了另外三个端做什么、做多重。 |
| 流程合理性 | 有硬伤 | **封面生成在"上传前"，标题生成在"上传后"**。如果封面要带标题/卖点，这个顺序是倒的（详见 §2.2）。 |
| 商业可行性 | 最大风险不在技术 | ① 模板版权；② 小程序没有天然流量。这两条必须在写第一行代码前想清楚。 |
| 结构合理性 | 桌面端最可疑 | 如果目的只是"批量出图"，服务端无头渲染就能做。桌面端存在的唯一硬理由：源文件必须用 Windows 上的 PowerPoint / Photoshop 打开才能渲染。 |

一句话总结：**方向对（批量供给 + AI 标注 + 小程序分发），流程要重排；先定"标准模板包"和"用户闭环"，再谈三个端。**

## 1. 先把我理解的流程画出来

```
【供给链路】

桌面端                          管理端                          服务端
┌──────────────┐   ┌────────────────────┐   ┌──────────────────────────┐
│ 导入模板文件  │──▶│ 上传封面 / 缩略图   │   │ 存储模板源文件            │
│ 批量生成     │   │ 批量上传模板文件    │──▶│                          │
│ 封面+缩略图  │   │ 调 DeepSeek 识别    │──▶│ 类型 / 标题 / 描述        │
└──────────────┘   └────────────────────┘   └───────────┬──────────────┘
                                                         │
【消费链路】                                              ▼
                                          用户打开小程序 → 浏览 → 详情 → ???（缺失）
```

我标出 **4 个断点**：

| # | 断点 | 位置 | 后果 |
| --- | --- | --- | --- |
| 1 | 封面/缩略图 与 模板文件 是**两次独立上传** | 桌面端 → 管理端 | 图文配对靠人工/文件名，批量时必错位 |
| 2 | 封面在**上传前**生成，标题在**上传后**生成 | 桌面端 → 服务端 | 封面若含标题/卖点，逻辑倒置，必须二次返工 |
| 3 | **详情页预览图**完全没有出现在流程里 | 桌面端/服务端 | 用户只看到一张封面，无法判断模板好坏，转化差 |
| 4 | 用户"拿到模板"之后发生什么，没有定义 | 小程序端 | 前面三个端没有验收标准 |

> 补充一句：你说的"管理端上传模板需要调用 DeepSeek 的 API Key"——**API Key 绝对不能放在管理端前端**。前端代码、浏览器 DevTools、抓包都能拿到，泄露后一天内会被刷爆。正确做法是管理端调你自己的服务端，服务端再调 DeepSeek（详见 §2.3）。

## 2. 逐环节拷打

### 2.1 总览：每个环节的一句话问题

| 环节 | 一句话拷打 |
| --- | --- |
| 桌面端 | 你究竟需要它来**渲染**，还是只是需要一个**批量按钮**？ |
| 管理端 | 叫"管理端"但只做上传，那它只是个上传器；真正的管理（审核/分类/上下架/数据）在哪？ |
| 服务端 | 除了存文件，它是不是还要负责 AI 队列、复核、权限、防盗链、支付？ |
| 小程序端 | 用户最后**拿走的是什么**？文件、图片、还是一句"去网盘下载"？ |
| 内容侧 | 这些模板从哪来？版权归谁？ |

### 2.2 桌面端（封面 / 缩略图）

**这是最需要重估的一环。**

#### 先回答 8 个问题

| # | 问题 | 为什么重要 |
| --- | --- | --- |
| Q1 | 模板源文件是什么格式？PPTX / DOCX / PDF / PSD / AI / 剪映草稿 / 视频 / 其他？ | 直接决定渲染方案，不同格式难度差 10 倍 |
| Q2 | 封面和缩略图是**从模板渲染出来的**，还是 **AI 生成的**？ | 如果是 AI 生图：与模板内容脱节、版权不清、一致性差，我不建议 |
| Q3 | 封面是"第 1 页裁切"，还是"重新设计一张带标题/卖点/角标的营销图"？ | 后者需要排版引擎，且依赖标题 → 与现在的流程顺序冲突 |
| Q4 | 一次批量多少个？单个模板多少页/多大？ | 决定进度、内存、失败重跑设计 |
| Q5 | 缩略图取第 1 页还是多页拼图？尺寸比例 3:4 / 16:9 / 1:1？ | 小程序列表布局依赖它，定错要全量重生成 |
| Q6 | 桌面端只支持 Windows，还是也要 macOS？给谁用（你自己 / 运营 / 外包）？ | 决定技术栈与分发方案 |
| Q7 | 生成完的图怎么到服务端？只落本地文件夹？谁上传？ | 这是断点 1 的根源 |
| Q8 | 失败怎么重跑？渲染卡死怎么办？渲染结果要不要人工肉眼验收？ | 批量任务必须有断点续跑与失败清单 |

#### 一个必须先解决的逻辑冲突

你的流程是「先出封面 → 后出标题」。那么：

- 如果封面**不含文字**（纯模板首屏渲染）→ 顺序 OK，但封面营销力弱，点击率靠模板本身颜值；
- 如果封面**含标题/卖点/角标**（大多数模板站的做法）→ **必须先生成标题**，封面要等到 AI 之后再做；
- 折中方案：封面做"A 版：纯渲染"和"B 版：渲染 + 标题合成"两种，B 版放到 AI 之后由服务端/桌面端二次合成。

**封面三种做法对比：**

| 方案 | 做法 | 依赖 | 什么时候做 | 评价 |
| --- | --- | --- | --- | --- |
| A 纯渲染裁切 | 第 1 页渲染成图，裁成列表/详情比例 | 渲染引擎 | 上传前 | 最轻，无文案，适合先跑通 |
| B 模板化合成 | 渲染页做底图 + HTML/Canvas 封面模板叠文字，截图导出 | 需要标题/卖点 | **AI 之后** | 转化最好，推荐二期 |
| C 文生图 | 调文生图模型画封面 | 文生图 API | 任意 | 与内容脱节、版权风险，不建议做主封面 |

#### 桌面端到底该不该存在？逐条检验

| 理由 | 成立条件 | 结论 |
| --- | --- | --- |
| ① 源文件必须用 Windows 商业软件渲染（PowerPoint COM / Photoshop / AI） | 你的模板确实是 PPTX/PSD/AI 且要求高保真 | 成立，桌面端必须 |
| ② 源文件太大，上传前先压缩/抽帧 | 视频/超大工程文件 | 成立，但也可以服务端做 |
| ③ 渲染耗时，想用本地算力、断点续跑 | 量大 | 成立，非必须 |
| ④ 操作者是运营，需要 GUI | 非技术人员 | 成立，但 GUI 可以后置 |

**如果 ① 不成立**，桌面端可以先降级为**命令行批处理工具**（同一套渲染逻辑）：省掉 GUI、安装包、Windows 签名、SmartScreen、杀软误报、自动更新这一整套成本——这些是典型的"隐形工期杀手"。

#### 渲染方案预研（按格式）

| 源格式 | 渲染方案 | 风险 |
| --- | --- | --- |
| PPTX / PPT | Windows：PowerPoint COM（保真最高，需装 Office）；跨平台：LibreOffice headless | 字体缺失导致排版漂移、SmartArt/动画丢失 |
| DOCX | Word COM / LibreOffice | 字体、页边距漂移 |
| PDF | MuPDF / pdfium / pdftoppm | 基本无风险 |
| PSD / PSB | Photoshop COM；或 psd-tools 导出合成预览 | 图层效果（智能对象/样式）不保真 |
| AI / EPS | Illustrator COM；或 Ghostscript | 字体、链接图丢失 |
| 图片 | Sharp / libvips | 无 |
| 视频 MP4 | ffmpeg 抽帧 | 编码、时长 |
| 剪映草稿 | 官方无开放渲染，只能先导出视频 | **不可自动化**，要提前确认 |

> **中文字体是最大的坑**：渲染机没装的字体，LibreOffice 会静默替换，出图"看着差不多但就是不对"。建议渲染机统一装字体包，或把字体随模板打包。

#### 输出物建议：不要输出"几张散图"，输出**标准模板包**

这是解决断点 1、3 的关键，详见 §3.1。

### 2.3 管理端（后台）

| # | 问题 | 我的判断 |
| --- | --- | --- |
| Q9 | "小程序管理端"到底是什么？是在**手机小程序里**做管理，还是**Web 后台**？ | 强烈建议 Web 后台。在手机小程序里批量上传几十 MB 的模板文件，体验是灾难（大文件、断点续传、文件选择、多选都受限） |
| Q10 | 管理端只做"上传"，还是也要 分类管理 / 审核 / 上下架 / 用户 / 订单 / 数据看板？ | 只做上传 = 上传器，不叫管理端。至少要覆盖"导入 → 复核 → 上下架" |
| Q11 | 批量上传一次多少个？要断点续传吗？重复文件要秒传吗？ | 100 个以上必须做直传对象存储 + 分片 + 断点续传；用文件 hash 做秒传与去重 |
| Q12 | 上传是"浏览器 → 你的服务端 → 对象存储"，还是"浏览器直传对象存储"？ | 必须直传，否则大文件全压服务端带宽 |
| Q13 | AI 识别是**同步**还是**异步任务**？ | 必须异步。上传 1000 个模板时同步调 DeepSeek，浏览器必超时 |
| Q14 | AI 生成完，**谁来点"上架"**？ | 必须有人工复核闸门。AI 直接上架 = 分类错、标题同质化、违规词风险 |
| Q15 | 需要多角色权限吗（上传 / 审核 / 超管）？ | 只有你自己一个人就先做单角色，别一开始上 RBAC |
| Q16 | 失败任务怎么补跑？AI 超时/限流怎么重试？ | 任务列表 + 失败筛选 + 一键重跑，是最低要求 |

**最关键的纠正：API Key 只能存在于服务端。**
管理端 → 你的服务端（带登录态）→ DeepSeek。服务端负责：限流、失败重试、用量记录、每日预算、key 轮换。

### 2.4 服务端

| # | 问题 | 我的判断 |
| --- | --- | --- |
| Q17 | 技术栈偏好？Node/TS、Java、Go、Python？ | 我倾向 Node/TypeScript 全栈：管理端、服务端、桌面端（Electron）共享类型与校验逻辑；若你团队是 Java/Go，就按团队来 |
| Q18 | 部署在哪？国内云 / 海外 / 微信云开发？ | 面向微信用户 → 国内云 + 备案域名 + HTTPS；微信后台要配 request/downloadFile 合法域名 |
| Q19 | 模板源文件存哪？对象存储 + CDN 是必须的 | 阿里 OSS / 腾讯 COS / R2 / S3 + CDN。**源文件私有读、签名 URL**，预览图可公开但加防盗链 |
| Q20 | 存储/流量成本算过吗？ | 1000 模板 × 20MB ≈ 20GB 存储；但**下载流量才是大头**，付费下载前先估算 |
| Q21 | 任务队列用什么？ | Redis + BullMQ（Node）够用；别上 Kafka |
| Q22 | 幂等怎么做？ | 用源文件内容 hash 做唯一键：同一文件重复导入不重复创建、不重复调 AI |
| Q23 | 数据模型定义了吗？"模板"的最小单位是什么？ | 必须先定。建议：模板 = 一套（可含多文件），预览图属于模板，标签多对多 |
| Q24 | 埋点/监控/备份？ | 从第一天就要有：上传成功率、AI 成功率、上架数、打开/收藏/下载漏斗；数据库每日备份 |

**AI 环节的工程细节（比"调一下 API"复杂得多）：**

1. **输入不能只有封面**。封面信息量有限（"蓝色商务 PPT"和"蓝色商务简历"封面可能长得一样）。建议输入：
   - 文件类型、页数、尺寸（**硬事实，用规则判断，不要问 AI**）
   - 从源文件抽出的文字：标题、目录、前几页文字（PPTX/DOCX 可直接解析，成本 0）
   - 封面图 + 前 3 页预览图（`deepseek-flash` 支持图片输入）
2. **输出必须结构化**：JSON schema + 预定义枚举（类型/风格/受众/场景），否则自由文本无法入库，人工清洗成本极高。
3. **标题会严重同质化**：批量几百个模板，AI 大概率产出"蓝色商务风 PPT 模板"×50。需要：要求基于"行业 + 场景 + 风格 + 卖点"组合生成、随机 few-shot 示例、生成后去重、相似度过高重生成。
4. **标题合规**：过滤"最/第一/100%/绝对"等极限词、敏感词；标题长度按小程序列表展示截断设计（如 16–24 字）。
5. **幂等 + 版本**：记录 prompt 版本、模型版本；规则改了要能批量重跑。
6. **成本估算**：`deepseek-flash` 视觉按图片尺寸折算 token（每图上限约 1024 tokens），1000 模板 × 4 张图 ≈ 400 万 input tokens 量级，token 成本不高；**真正的成本是人工复核时间**。
7. **失败兜底**：AI 挂了不能阻塞上架，要有"先用文件名/人工填标题"的降级路径。

**数据模型草案（供讨论）：**

```
templates        id, source_hash(唯一), status, category_id, title, subtitle, description,
                 cover_key, thumb_key, package_key, page_count, file_size, created_at, published_at
template_files   template_id, role(source|preview|thumb|cover), object_key, mime, size, width, height, seq
categories       id, parent_id, name, sort, icon
tags             id, name, type(style|scene|audience)
template_tags    template_id, tag_id
ai_jobs          id, template_id, status, model, prompt_version, input_tokens, output_tokens,
                 cost, result_json, error, attempts, created_at
users, favorites, downloads, orders(二期才做)
```

**状态机（必须一开始就定）：**

```
draft → packaging → uploaded → ai_pending → ai_done → review_pending → published / rejected / failed
```

### 2.5 小程序端（用户端）

#### 最重要的问题：用户到底"拿到什么"？

| # | 问题 | 说明 |
| --- | --- | --- |
| Q25 | **用户选完模板后如何获得它？** | 见下方四种模式，这决定整个产品形态 |
| Q26 | 模板是"文件"还是"可在线套用的内容"？ | 两者是完全不同的产品 |
| Q27 | 要付费吗？付费方式是会员、单模板、还是免费+广告？ | 决定支付/订单/会员体系要不要做 |
| Q28 | 需要在详情页看多页预览吗？ | 只看封面 = 转化率低；预览图谁生成要回到供给链路里 |
| Q29 | 搜索怎么做？分类 + 关键词 + 标签？ | 数据量小用数据库 LIKE 就够，别一上来上 ES |
| Q30 | 列表图片规范定了吗？ | 见下方"三件套" |
| Q31 | 要做收藏 / 分享 / 历史吗？ | 低成本高价值，建议一期就有 |
| Q32 | 埋点漏斗怎么设计？ | 打开→列表→详情→点击获取→支付/下载，每一步都要埋 |

**四种用户获得模板的方式（差别巨大）：**

| 模式 | 用户动作 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 预览 + 下载文件 | 点下载 → `wx.downloadFile` → `wx.openDocument` → "发送给朋友/用其他应用打开" | 最轻、最快上线 | 微信内拿不到电脑上；大文件慢；付费后仍可能被转发盗版 |
| B. 小程序内直接套用/编辑 | 选模板 → 改文字/图片 → 导出图片/文件 | 用户价值最高、留存最好 | 工作量最大，是另一个产品；模板要变成结构化数据 |
| C. 展示 + 引导到私域/网盘 | 点按钮 → 客服/公众号/企微/复制链接 | 变现灵活 | 跳转受限、链路长、转化低，且审核有风险 |
| D. 纯展示 + 广告 | 无下载，靠流量主广告 | 最容易过审 | 收入依赖流量，而小程序没有天然流量 |

> 这四种没有对错，但**必须选一个**。如果不选，前面三个端都是在给一个不存在的闭环供货。

**图片"三件套"规范（建议先定死）：**

| 图 | 用途 | 建议规格 | 数量 | 生成方 |
| --- | --- | --- | --- | --- |
| thumb 缩略图 | 列表 / 瀑布流 | 3:4 或 16:9，宽 400–600，WebP ≤ 50KB | 1 | 桌面端 |
| cover 封面 | 详情页头图 / 推荐位 | 宽 1080–1440，WebP ≤ 200KB | 1 | 桌面端（云合成版可后置） |
| preview 预览页 | 详情页滑动浏览 | 宽 1080，WebP ≤ 120KB/张，只取前 3–6 页 | 3–6 | 桌面端 |
| 水印预览 | 未授权用户可见 | 预览图叠加水印 | 同上 | 服务端动态或预生成 |

### 2.6 内容与版权（最大风险，没有之一）

| # | 问题 | 说明 |
| --- | --- | --- |
| Q33 | 模板从哪来？自产原创 / 采购授权 / 网络收集 / 混合？ | **网络收集的模板用于售卖，是最容易被投诉、被下架、被索赔的做法**。小程序审核会看版权材料，字体/素材/人像都有独立版权 |
| Q34 | 模板里的字体、图片、人像有商用授权吗？ | 字体侵权是模板行业高发问题（尤其"微软雅黑/方正"类） |
| Q35 | 冷启动内容从哪来？前 100–1000 个模板怎么攒？ | 没有内容，小程序就是空壳；内容质量决定留存 |
| Q36 | 谁来保证质量分级？（垃圾模板一次就流失用户） | 需要人工精选 / 评分 / 下架机制 |
| Q37 | 小程序类目、主体资质、备案准备好了吗？ | 个人 / 个体户 / 企业的可做类目、支付能力不同 |
| Q38 | 上线后的流量从哪来？搜一搜 / 分享 / 公众号 / 视频号 / 投放？ | **小程序没有应用商店分发**，"上线"不等于"有人用" |

## 3. 我建议的 v1 流程（待你拍板后确认）

核心思想：**把"标准模板包"作为三端唯一契约，让各端解耦。**

### 3.1 契约：标准模板包（Template Package）

一个模板 = 一个包（文件夹或 zip）：

```
package/
  manifest.json      # 元信息（见下）
  source/            # 源文件（可多个）
  text.json          # 从源文件抽取的文字（标题/目录/前几页），供 AI 用，成本 0
  preview/           # 1..N 张预览图 1080 宽 WebP
  thumb.webp         # 列表缩略图
  cover.webp         # 封面（A 版纯渲染；B 版可后置）
```

`manifest.json` 关键字段：

```json
{
  "packageVersion": 1,
  "sourceHash": "sha256",
  "title": null,
  "type": null,
  "sourceFile": "source/xxx.pptx",
  "pageCount": 24,
  "renderEngine": "powerpoint-com@1.0.0",
  "fontPack": "fonts-2026.1",
  "generatedAt": "2026-11-01T10:00:00+08:00"
}
```

**这个包带来的好处：**

1. 桌面端可完全离线跑，不依赖服务端；
2. 管理端上传的是"包"，图和文件天然配对，**断点 1 消失**；
3. 服务端只做结构校验 + 入库，不关心渲染；
4. 换渲染引擎 / 重新生成封面 / 补预览页，都只影响包，可重跑。

### 3.2 修正后的供给链路

```
桌面端(CLI/GUI)                     服务端                          管理端(Web)
导入文件夹
  → 逐个渲染/抽文字/生成三件套
  → 生成标准包
  → 本地校验(缺图/缺源文件)
  → 扫描直传对象存储  ──────▶ 创建草稿(按 sourceHash 幂等)
                               → 入队 AI 任务(异步)
                               → DeepSeek 结构化输出
                               → 待复核队列          ──────▶ 复核/分类/改标题
                                                          → 人工点"上架"
                                                          → 上架
```

**关键改动：**

1. **桌面端直传**，管理端只做"管"（也保留手动上传入口做兜底）；
2. AI 在服务端**异步队列**里跑，幂等 + 重试 + 预算；
3. **人工复核是必经闸门**，不是可选项；
4. 全链路状态机，任何一步失败都能定位、重跑。

### 3.3 消费链路（需你选模式 A/B/C/D 后再细化）

以模式 A（预览 + 下载）为例：

```
打开小程序 → 首页(分类/搜索/推荐) → 列表 → 详情(封面+多页预览+标签+同款推荐)
  → 点"获取模板" → 登录/会员校验 → 生成签名下载 URL → 下载/打开文件 → 收藏/分享
```

### 3.4 三端职责表

| 端 | 职责 | 明确不做 |
| --- | --- | --- |
| 桌面端 | 渲染、抽文字、生成三件套、打包、上传 | 不直接调 DeepSeek、不存业务数据 |
| 管理端(Web) | 导入/上传、AI 结果复核、分类标签、上下架、用户/订单/数据 | 不持有 API Key、不做重渲染 |
| 服务端 | 存储/CDN、内容 API、AI 代理与队列、权限、支付、状态机 | 不做保真渲染（除非格式简单如 PDF） |
| 小程序端 | 浏览、搜索、详情、获取、收藏、分享、埋点 | 不做编辑（除模式 B） |

## 4. 技术前提核实

### 4.1 DeepSeek 视觉：成立 ✅

- 官方文档确认：`deepseek-flash` 接受图片输入，支持 base64 / 外部 URL / Files API，格式 JPEG/PNG/GIF/WebP，单图 ≤ 32MiB，单请求最多 600 张图。（[Vision | DeepSeek API Docs](https://api-docs.deepseek.com/guides/vision/)）
- 图片会按尺寸折算 token，每图上限约 1024 tokens——**成本可控**。
- 但注意：AI 看的是"图"，不是源文件。**只给封面识别准确率不够**，建议叠加"抽取的文字 + 前几页预览"（见 §2.4）。
- API Key 必须服务端持有。

### 4.2 小程序液态玻璃：可行，但有工程坑 ⚠️

| 渲染器 | `backdrop-filter` 情况 | 结论 |
| --- | --- | --- |
| WebView（默认） | 支持度较好（iOS / 较新安卓），但低端安卓 GPU 弱会掉帧，官方未作为稳定承诺 | **推荐走 WebView** |
| Skyline | 支持 `backdrop-filter`，但**只允许单个 filter 函数**（不能 `blur()+saturate()` 组合）、不支持 `drop-shadow()`、`mask-image` 不支持渐变；而液态玻璃的高光/折射几乎都靠多层渐变与 mask 叠加 | 1:1 复刻成本高，不推荐一期上 Skyline |

第三方整理参考：[Skyline 与 WebView WXSS 差异参考](https://github.com/didi/mpx/blob/3fcd0da052a028e0204a4b7f6db7e1d2ca788087/.agents/skills/mpx2skyline/references/skyline-style-reference.md)（非官方，仅作预研）。

**建议：**

1. 做"液态玻璃**风格**"，不做 iOS 26 的 1:1 复刻；
2. 封装统一组件：`glass-bar` / `glass-card` / `glass-button` / `glass-sheet`，全站复用；
3. 尊重 Apple 原始原则：**玻璃只用于"浮在内容之上的控制层"**（导航栏、TabBar、浮动按钮、弹层、筛选栏），不要拿玻璃铺满整屏卡片，否则可读性、性能双崩；
4. 必须有降级方案：检测不支持时退化为"半透明 + 高斯模糊底图 + 渐变描边 + 高光动画"；
5. 性能红线：一屏内 `backdrop-filter` 元素 ≤ 2–3 个；动画只用 `transform/opacity`；滚动中不要实时 blur；
6. 需要真机矩阵验证（iOS 新旧机型 + 安卓高中低端 + 深色模式）。

### 4.3 微信侧现实约束 ⚠️

- **下载**：小程序内拿到文件后，只能 `openDocument` 后"发送给朋友 / 用其他应用打开"；PC 端有 `saveFileToDisk`。**"手机上看中、电脑上用"这个链路体验有损**，必须在产品设计时先解决或明确告知用户。
- **付费**：微信有官方"虚拟支付"能力（文档覆盖个人、企业、个体户）与"会员订阅（安卓/鸿蒙、iOS）"，说明有正规通道（[虚拟支付文档入口](https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment.html)）；但能否开通、费率多少取决于你的**主体身份与类目**，以官方最新文档和审核结果为准。**不要用"跳转外部收款/个人收款码"绕过**，这是下架高发项。
- **广告**：小程序流量主有开通门槛（UV 要求），收入依赖流量，不能作为首发变现假设。
- **类目与版权材料**：模板属于内容型服务，审核可能要求版权证明；网络收集的模板风险极高。
- **域名**：request / downloadFile / uploadFile 合法域名需 HTTPS 且已备案。

## 5. 如果只记三条优化

1. **先砍端，别三个 GUI 同时开工。**
   桌面端 v1 先做 CLI/批处理（渲染逻辑不变），管理端做 Web，小程序一期只做"浏览 + 详情 + 收藏 + 埋点"。等全链路跑通，再补 GUI 和下载/支付。
2. **先定契约，再写代码。**
   标准模板包 + 状态机 + AI 输出 JSON schema，这三样定错，后面全返工。
3. **先验需求，别自嗨。**
   在正式开发前，用 20–50 个真实模板手工跑通全链路（可以半手工），验证：渲染保不保真、AI 标题能不能用、用户会不会点、愿不愿意付费。供给侧自动化做得再好，需求侧不成立就是白干。
