| 维度 | 判断 | 一句话依据 |

| 产品可行性 | **有条件可行（5/10）** | 作为"大而全模板库"大概率失败；作为"垂直场景 + 精选 + 双交付"有机会。 |

## 1. 产品视角

### 1.1 先把核心循环和指标摊开

```
用户侧：搜一搜 / 分享卡片 / 私域 → 列表 → 详情 → 复制短链
        → 网盘 App 打开 → 保存 → 下载 → PC 使用
你侧：  模板源文件 → CLI 渲染 → 上传 → 网盘同步 + AI 标注 → 复核 → 上架
```

**核心指标只有一个：详情页 → 复制链接率。** 它同时代表"模板吸引力"和"页面转化设计"。其余指标：

| 指标 | 一期目标（建议） | 说明 |
| --- | --- | --- |
| 详情页 → 复制链接率 | ≥ 20–25% | 低于 15% 说明模板或详情页有问题 |
| 列表 → 详情点击率 | ≥ 15% | 封面质量直接决定 |
| 分享率 | ≥ 3% | 小程序裂变的主要来源 |
| 7 日回访率 | 可能 < 5% | 低频需求，接受现实，别硬做留存 |
| 搜索词有量数 | ≥ 20 个 | 验证搜一搜入口是否成立 |

### 1.2 五个必须正视的产品问题

**① 渠道问题：小程序没有天然流量。**
微信不会凭空给流量。入口只有：搜一搜、聊天分享、公众号/视频号/私域引流、线下码。竞品（稻壳、WPS、包图、优品PPT、小红书、公众号）已经占住用户心智和搜索词。你唯一低成本的入口是**搜一搜 + 页面收录**，这要求标题、分类、页面结构都为搜索优化——不是"上架了就会有人来"。

**② 留存问题：模板是低频需求。**
用户找模板 = 一次性任务，下载完就走。这个产品更接近"内容站/SEO 资产"，不是"习惯型产品"。因此不要在设计上投入过多"留存功能"（签到、积分、社区），把精力放在**获取新客的内容供给**上。

**③ 交付摩擦：网盘链路有 3–5 步。**
复制 → 打开网盘 App → 保存 → 下载 → 电脑登录。百度非会员有下载限速，20MB 的 PPT 可能要几分钟；链接失效、提取码输错都是流失点。**这是方案里体验最弱的一环。**

**④ 变现问题：免费模板是红海。**
用户能找到大量免费模板；付费意愿集中在"垂直场景 + 高质量 + 可商用授权"。个人主体虚拟支付可以做（wallpaper-manager 已验证），但没有品牌信任、没有独家内容时，转化会很低。广告收入需要大流量（流量主有 UV 门槛），不能当首发假设。

**⑤ 供给不是护城河。**
桌面 CLI + AI 标注解决的是**你自己的运营效率**，用户感知不到。用户感知到的只有：模板好不好看、搜不搜得到、下载顺不顺。**差异化必须来自内容和场景，不能来自工具链。**

### 1.3 定位建议：收窄到 1–2 个垂直场景

"大而全模板库"是红海正面战场，建议选垂直：

| 候选 | 优势 | 风险 |
| --- | --- | --- |
| A. 教师课件 / 教学设计 | 刚需、高频、竞品分散、可自创 | 单份价值低、需要懂教学 |
| B. 大学答辩 / 毕业设计 | 季节性爆发、搜索词明确、学生传播强 | 季节性强，淡季空 |
| C. 党政 / 国企汇报 | 付费意愿高、要求规范 | 版权敏感、内容门槛高、需资质 |
| D. 求职简历 / 面试 | 需求大、模板标准化 | 红海、免费资源极多 |

选择标准：**搜索词量 × 你能持续产出的能力 × 付费意愿 × 竞争密度**。建议先选 A 或 B 跑 2 周，用数据说话。

### 1.4 低成本、高价值的产品增强

1. **双交付（强烈建议）**：小程序内直接打开 + 转发（`wx.openDocument` 支持 pptx/docx/pdf），同时保留网盘长期保存。这能显著降低"手机看、电脑用"的摩擦——比网盘快得多。需要实测 `downloadFile` 对大文件（20–50MB）的限制和流量成本。
2. **搜一搜/页面收录优化**：标题按「场景 + 风格 + 格式」结构化生成（AI 标注天然适合干这个），页面可被收录。这是低成本获客的唯一抓手。
3. **场景合集/清单**：如"答辩全套""期末评语合集"，提升单次获取量、增加分享动机。
4. **模板适配信息**：页数、格式、是否含图表、字体、是否可编辑——降低"下载后不能用"的挫败感，提升复购/口碑。
5. **分享卡片优化**：转发标题 + 5:4 分享图；支持分享到朋友圈（`onShareTimeline`）。
6. **（可选）AI 前台化**：用户描述场景 → 推荐模板 + 生成标题/大纲。可以成为真差异，但会扩大范围，建议二期评估。

### 1.5 两周一页纸的验证计划（成本极低）

| 项 | 内容 |
| --- | --- |
| 供给 | 50–100 个模板（优先自创/授权），手工整理，不一定走自动化 |
| 入口 | 选 1 个渠道：小红书 / 公众号 / 视频号 / 私域，发 10–20 条内容 |
| 落地 | 小程序首页 + 详情页 demo（数据可先写死/静态 JSON） |
| 观测 | 详情→复制率、列表点击率、搜索词、分享率、用户反馈 |
| 判定 | 复制率 < 15% 或基本无流量 → 先别做自动化，改定位/改内容 |

**这 2 周不是浪费：它能替你省掉 4–6 周的无效自动化建设。**

## 2. 技术视角

### 2.1 可行性矩阵

| 环节 | 结论 | 风险 | 关键点 |
| --- | --- | --- | --- |
| LibreOffice 渲染 PPT/Word | 可行 | **中高** | 保真度是唯一硬骨头（SmartArt/图表/艺术字/字体） |
| OOXML 文字抽取 | 可行 | 低 | 解 zip 读 XML，不依赖 Office |
| PDF → 图片 / 裁剪 / WebP | 可行 | 低 | pdfjs + sharp，Windows 预编译可用 |
| 分片上传 + 断点续传 | 可行 | 中 | 实现成本在服务端与 CLI 两侧 |
| 网盘同步（百度+夸克） | 可行 | **高** | 账号风控、上行带宽、Skill Beta、夸克无删除 |
| 短链 + 提取码 | 可行 | 低 | wallpaper-manager 已验证 |
| DeepSeek 标注 | 可行 | 中 | 准确率/标题同质化可解，成本极低 |
| 小程序（原生 + 液态玻璃） | 可行 | 中 | 玻璃性能、文件直开限制、包体积 |
| 服务端（NestJS + Prisma） | 可行 | 低 | 与 wallpaper-manager 同规模已验证 |
| 部署（宝塔同机） | 可行 | 低 | 新目录 + 独立库 + 独立 Redis |

### 2.2 三个被低估的隐藏成本

**① 渲染调优（1–2 周，不是 3 天）**

LibreOffice 对 PPTX 的高保真渲染有明确短板：
- SmartArt、图表、艺术字、3D、复杂渐变、母版效果 → 大概率失真；
- 特殊字体（方正/思源/站酷等）缺失 → 静默替换，版面漂移；
- 嵌入字体（Office 内嵌字体）LibreOffice 不识别；
- 加密文件、损坏文件、超大文件会直接卡住。

必须做的事：
- 用 50 个真实模板量化"可接受率"（目标 ≥ 85–90%）；
- **字体检测**：解析 OOXML 里的 `typeface` 列表，`templio doctor` 校验本机字体，输出缺失清单；
- LibreOffice 并发：每个 worker 独立 `-env:UserInstallation`，避免单实例锁；
- 单文件超时必须 kill，中文路径用 ASCII 临时目录规避编码问题；
- 产品兜底：管理端可替换封面/预览、可标记"渲染不可用"。

**② 网盘批量（最大运营风险，不是技术风险）**

- **上行带宽**：1000 个模板 × 20MB = 20GB。服务器 5Mbps ≈ 9 小时，10Mbps ≈ 4.5 小时，100Mbps ≈ 27 分钟。首次上架可能占用一整天；还要确认服务器出网是否计费。
- **账号风控**：短时间大量上传 + 大量创建分享，可能触发限流甚至封号。**必须先做 50 个文件压测**，观察上传速度、失败率、是否触发验证；再决定分批、间隔、会员账号策略。
- **夸克没有删除命令**：重复上传会堆积文件。文件名用 `hash`、目录按批次、逻辑上只传一次。
- **百度 Skill 作用域限制** `/apps/bdpan/`：分享路径必须在该目录下（wallpaper-manager 已按这个配置）。
- **官方 Skill 处于公测（BETA）**：命令、授权流程可能变化 → 封装一层适配层 + 探活 + 版本锁定。
- **分享失效**：永久分享也可能被平台处置 → 至少要有手动失效标记，P2 再做自动检测。

**③ 图片 CDN 缺失（v1 方案没写）**

封面/预览图必须走 CDN/对象存储，否则：
- 全国用户访问宝塔服务器，首屏会慢；
- 图片流量会吃掉服务器带宽，影响 API；
- 微信小程序 `<image>` 可以加载任意 HTTPS 域名（不需要 request 白名单），但仍需 HTTPS。

建议：OSS/COS + CDN（或七牛/又拍）；图片域名独立；后续付费内容加防盗链。粗算 1000 模板图片约 1.1GB，月流量 20–50GB，成本十元级。

### 2.3 其他技术缺口（v1 未覆盖）

| # | 缺口 | 说明 |
| --- | --- | --- |
| 1 | 双交付实测 | `wx.downloadFile` 对大文件有上限（历史上有过限制），需实测 20–50MB pptx |
| 2 | 小程序包体积 | 主包 ≤ 2MB；玻璃组件与图标要控制 |
| 3 | 自定义 tabBar + backdrop-filter | 切页可能闪烁，需固定 tabbar + 稳定页面背景 |
| 4 | 页面收录/搜一搜 | 小程序页面可被微信搜索收录，需标题/结构优化 |
| 5 | 分享卡片 | 转发标题/图、朋友圈 `onShareTimeline` |
| 6 | 隐私协议 | 登录/收藏需要用户隐私保护指引 |
| 7 | 类目与合规 | 模板属于内容型服务，类目与版权材料要提前确认 |
| 8 | 埋点看板 | 详情→复制核心漏斗要能看见 |
| 9 | 文件安全 | pptx/docx 本质是 zip：防 zip 炸弹、路径穿越、超大文件 |
| 10 | CLI 鉴权 | 专用可吊销 Token，不要复用管理端账号密码 |

### 2.4 时间估算修正（有真实参照）

`wallpaper-manager` 的实际工期：**2026-08-21 首个提交 → 2026-10-29 最近提交，379 次提交，约 23.6k 行**（api 14.0k / admin 4.3k / miniprogram 5.2k / shared 0.05k），约 **10 周**。

模板宝 的 MVP 范围相当（服务端 + 管理端 + 小程序 + 桌面 CLI + 网盘 + AI + 渲染），因此：

| 阶段 | v1 估计 | 修正估计 | 差异原因 |
| --- | --- | --- | --- |
| P0 打样 | 3–5 天 | **1–2 周** | 渲染调优、字体、真机玻璃、网盘 50 文件压测 |
| P1 供给自动化 | 2–3 周 | **4–6 周** | 四端全量 + 网盘/短链 + 复核 + 埋点 |
| P2 GUI/商业化 | — | +3–4 周 | 桌面 GUI、支付、订单对账 |
| **总计到可用 MVP** | ~3 周 | **6–8 周** | 一个人 + AI 辅助的节奏 |

## 3. 三个一票否决 gate（建议写进计划）

| Gate | 验证方式 | 通过标准 | 不通过怎么办 |
| --- | --- | --- | --- |
| **G1 渲染保真** | 50 个真实 PPT/Word 批量渲染，人工抽检 | 可接受率 ≥ 85–90% | 换引擎（Office COM/商业库），或产品降级为"封面 + 单页预览" |
| **G2 网盘批量** | 50 个文件连续上传 + 建分享 | 无限流/封号；单文件 ≤ 3 分钟；链接可打开 | 改分批/间隔、换夸克为主、或改直链交付 |
| **G3 需求验证** | 50–100 模板 + 2 周引流 | 详情→复制 ≥ 20–25%，有自然搜索词 | 不做 P1 自动化，重做定位/内容 |

**P0 只做这三件事 + 一个可交互 demo。三个 gate 全过，才投 P1。**

## 4. 对 v1 流程确认稿的修订建议（12 条）

1. **新增 CDN/对象存储**（封面/预览长期存储 + 加速），本地存储只做中转。
2. **新增"双交付"**：小程序内直接打开/转发 + 网盘长期保存（需实测文件大小限制）。
3. **CLI 增加字体检测**（OOXML typeface 列表 → doctor 校验），并统一字体包。
4. **新增网盘 50 文件压测 + 分批/间隔策略 + 夸克 hash 命名策略**。
5. **新增网盘链接失效标记/检测**（一期手动，二期自动）。
6. **新增搜一搜页面收录 + 分享卡片优化**（标题结构化、onShareTimeline、5:4 分享图）。
7. **新增隐私协议、类目资质、投诉下架流程**。
8. **修正时间表**：P0 1–2 周，P1 4–6 周，总计 6–8 周。
9. **收窄定位**：先锁定 1–2 个垂直场景，不做大而全。
10. **新增三个 gate**（G1/G2/G3）作为阶段门禁。
11. **新增埋点看板**（详情→复制漏斗、搜索词）。
12. **新增成本预算表**（存储/CDN/AI/网盘会员）。

## 5. 最终判断

- **技术：可行。** 按 v1 架构能落地，没有架构级阻塞；最大技术风险是渲染保真和网盘批量，都可以在 1–2 周内用真实样本验证。
- **产品：有条件可行。** 成败不在自动化，而在"选对垂直场景 + 内容质量 + 流量入口"。大而全会输，垂直化才有机会。
- **计划：需要改。** 三个 gate 前移、时间 ×1.5–2、补 CDN 与双交付。
- **建议路径：** 先 P0（1–2 周，验证 G1/G2/G3）→ 全过再投 P1（4–6 周）→ 然后才是 GUI/商业化。

> 一句话：**这套方案的技术风险可控，产品风险不可控；先把产品风险用两周压到最低，再花钱买自动化。**
